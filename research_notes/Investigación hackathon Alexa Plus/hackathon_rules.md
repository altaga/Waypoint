## Q2. What exactly must an Alexa+ submission contain? Is a self-hosted MCP server plus a web MCP client or simulated Alexa+ host acceptable?

### Takeaway
Yes, this setup is explicitly acceptable.
- **The MCP path.** Build a "self-hosted MCP server, implementing MCP spec version 2025-11-25 (or a later version, once confirmed) over Streamable HTTP". The repo must import and call this at runtime.
- **The simulated path.** Alternatively, submit a "simulated Alexa+ experience", which is exempt from the runtime-hook rule.
- **What the FAQ says.** A web page that is a real MCP client (initialize, tools/list, tools/call over Streamable HTTP) "satisfies the requirement". Real Alexa+ integration is impossible for participants.

### Cited Findings
**Track requirement (verbatim)**
- "Alexa+: A working Agent Skill or a self-hosted MCP server, implementing MCP spec version 2025-11-25 (or a later version, once confirmed) over Streamable HTTP. Alternatively, entrants may submit a simulated Alexa+ experience instead — built using any AI or agentic tool of their choice, no specific framework, SDK, or MCP-shaped surface required. This alternate path is exempt from the runtime-technology-hook requirement above; the code repository must still include the simulation's source code, and the demo video must clearly show the simulated experience." — [Rules §4, Submission Requirements](https://amazonappdev2026.devpost.com/rules)
- **The runtime "hook" rule:** "For Alexa+, Bee, and Ring: The repository must demonstrate use of your track's required technology at runtime in your code — imported and actually called (a library import, an app/backend entry point, or a loaded agent/flow/MCP config), not just named in the README." — [Rules §4](https://amazonappdev2026.devpost.com/rules)
- Overview wording:
  - "Build a self-hosted MCP server (spec 2025-11-25 or later, Streamable HTTP) or an Agent Skill. MCP is the open standard that powers Alexa+ integrations. New to MCP? Build a simulated Alexa+ experience in a web app using your preferred agentic tool."
  - "Alexa+: show your Agent Skill or MCP server (spec 2025-11-25+, Streamable HTTP) in action."
  - Source: [Overview](https://amazonappdev2026.devpost.com/)
- How to enter (Alexa+): "Develop an MCP following the open-source docs: modelcontextprotocol.io/docs/latest/getting-started/intro". — [Rules §4](https://amazonappdev2026.devpost.com/rules)
- Resources page, Alexa+ section: "Build a working MCP (Model Context Protocol) integration on the open standards for Agent Skills and Streamable HTTP transports. You can simulate an Alexa+ experience using your preferred agentic tools via a web app." It links to only two items:
  - https://apps.extensions.modelcontextprotocol.io/api/#build-with-agent-skills
  - https://modelcontextprotocol.io/specification/2025-11-25/basic/transports#streamable-http
  - Source: [Resources](https://amazonappdev2026.devpost.com/resources)

**FAQ: the web MCP client path (verbatim)**
- Question: "For the Alexa+ track, can I demo my self-hosted MCP server through a web page that acts as a real MCP client, instead of a device?"
- Answer: "Yes. A web page that acts as an actual MCP client (sending initialize, tools-list, and tools-call requests over Streamable HTTP) satisfies the requirement - this is the simulated-experience path the Resources page points to, since there's no way for any participant to connect a self-hosted MCP server to a real Alexa+ device or developer console (that tooling is select-partners-only). Showing an existing AI assistant app calling the same server is a nice bonus, but not required."
- Source: [FAQ](https://amazonappdev2026.devpost.com/details/faqs)

**FAQ: hardware**
- "Alexa+: build a self-hosted MCP server or Agent Skill, or a simulated experience - no physical device needed." — [FAQ](https://amazonappdev2026.devpost.com/details/faqs)

**Forum clarifications on the simulated web experience (Emerson Sklar, ~Sep 2026)**
- Must it look like Alexa? "No, but that certainly helps with the Design portion of the judging criteria".
- Is a dynamic agent needed? "no, you can just simulate it (and you'll have no way to actually call Alexa+ anyway)".
- Voice: "Voice input/output is not required".
- Custom UI for cards and results: "Absolutely".
- Must it identify itself as a simulation? "Not required".
- Can the backend be real while only the Alexa+ layer is simulated? "Yes".
- Design references: the Alexa+ add-on design guide (https://developer.amazon.com/docs/alexaplus/add-ons/mcp-addon-design-guide-overview.html) and apl.ninja.
- What the video must show: "It just must look / feel / sound / etc. like it's actually functional and be something that could reasonably be an interesting use case on Alexa."
- Source: [Forum 45058](https://amazonappdev2026.devpost.com/forum_topics/45058-clarification-on-simulated-alexa-web-experience-requirements)

**Other forum clarifications**

Also, Lovable can create MCP servers ... for a non-simulated experience." — [Forum 45058](https://amazonappdev2026.devpost.com/forum_topics/45058-clarification-on-simulated-alexa-web-experience-requirements)
- Demo options with no devices:
  - "for Alexa, you could create a simulated web frontend or even create an Alexa Skill (the technology for building for the original Alexa) and demo your MCP being called from that."
  - "No UI is required, but you do need some way to demo it."
  - A Node.js simulator calling tools/call and printing to a terminal "could be [an] option".
  - Source: [Forum 45263](https://amazonappdev2026.devpost.com/forum_topics/45263-demo-video)

- Features the add-on platform does not support may still be shown: "you absolutely could demo it as part of your submission (since the submissions and judging criteria aren't bound by the publicly documented addon capabilities)." — [Forum 45199](https://amazonappdev2026.devpost.com/forum_topics/45199-alexa-mcp-can-an-add-on-initiate-alexa-to-alexa-calling-or-drop-in)

**Significant-update rule**
- Projects must be "newly created ... or ... significantly updated after the start of the Hackathon Submission Period. Entrants must explain how their Project was significantly updated". — [Rules §4](https://amazonappdev2026.devpost.com/rules)
- FAQ on the same point: "A new conversational feature that brings new functionality to an existing app can count as a significant update - focus your demo on a clear before-and-after". — [FAQ](https://amazonappdev2026.devpost.com/details/faqs)

### Inferences
- The strongest compliant setup is all of the following together:
  1. A real Streamable-HTTP MCP server (2025-11-25) built on the official SDK. This satisfies the hook rule outright.
  2. A web host that is a genuine MCP client.
  3. Optionally, a second client calling the same server, such as an AI assistant app or a Strands agent. The FAQ calls this "a nice bonus".
- Claiming the MCP-server path, not only the simulated path, avoids any doubt about Stage One's "reasonably applies the required APIs/SDKs" check.
- "Later version, once confirmed": no forum post or update was found confirming MCP 2026-07-28. Staying on 2025-11-25 is the safe choice.

### Gaps
- No official definition of "Agent Skill" for this track beyond the Resources link to MCP Apps' "Build with Agent Skills".
- The 3-Sep Build Session video (https://youtu.be/ws61g53S2b4) was not transcribed, so its Alexa+ segment and judging Q&A were not reviewed.

## Q3. Judging criteria (verbatim), weights, what is penalized, and bonus points

### Takeaway
- **Stages.** Stage One is pass/fail on viability and use of the required APIs. Stage Two scores four **equally weighted** criteria: Tech Implementation, Design, Potential Impact, Quality of the Idea. An update says each is scored 1–5.
- **"Obvious" Alexa+ ideas.** These are named as "single-turn Q&A bot, basic MCP wrapper around an existing API".
- **Bonus.** Friction logs can earn up to a 10% bonus.

### Cited Findings
**Stage One**
- "Stage One) The first stage will determine via pass/fail whether the ideas meet a baseline level of viability, in that the Project reasonably fits the theme and reasonably applies the required APIs/SDKs featured in the Hackathon." — [Rules §6](https://amazonappdev2026.devpost.com/rules)

**Stage Two criteria**
- Stage Two uses "equally weighted criteria". — [Rules §6](https://amazonappdev2026.devpost.com/rules)
- **Tech Implementation**: "How well is the project built, and how effectively does it use the required tech? Does it effectively leverage the required APIs, SDKs, or device capabilities for the specified track (Fire TV, Alexa+, Bee, or Ring) or mini-challenge (AWS Builder, Open Source)?" — [Rules §6](https://amazonappdev2026.devpost.com/rules)
- **Design**: "Does the project deliver a complete, coherent product experience? Is the interaction model intuitive and well-considered for the target device or platform?" — [Rules §6](https://amazonappdev2026.devpost.com/rules)
- **Potential Impact**: "Does the project make a credible, specific case for solving customer needs? Could it realistically serve an audience beyond the hackathon?" — [Rules §6](https://amazonappdev2026.devpost.com/rules)
- **Quality of the Idea**: "Is this a creative, imaginative use of the required tools? Does the team demonstrate a genuine understanding of the developer ecosystem and the end-user needs within their chosen track? Judges should distinguish creative ideas from obvious ones". — [Rules §6](https://amazonappdev2026.devpost.com/rules)
- Alexa+ examples (verbatim): "Alexa+: Obvious: single-turn Q&A bot, basic MCP wrapper around an existing API. Creative: agentic workflow that orchestrates across services autonomously, context-aware add-on that maintains state across sessions, purchasing capabilities, media support (cards, carousels, etc), MCP Apps [link: https://modelcontextprotocol.io/extensions/apps/overview], Agent Skills." — [Rules §6](https://amazonappdev2026.devpost.com/rules)
- AWS Builder examples: "Obvious: single Bedrock call for text generation, S3 for storage. Creative: multi-service pipeline (Bedrock + AgentCore + Strands), agentic architecture with Claude/Kiro for development workflow, agent orchestration patterns." — [Rules §6](https://amazonappdev2026.devpost.com/rules)
- Open Source examples: "Obvious: README update, typo fix, minor formatting. Creative: meaningful feature addition with tests, bug fix that unblocks other developers, new integration pattern". — [Rules §6](https://amazonappdev2026.devpost.com/rules)

**Scoring and bonus**
- The 1–5 scale: "Every submission is scored 1 to 5 on four equally weighted criteria: Technical Implementation, Design, Potential Impact, and Quality of the Idea." — [Update "Got an idea?" (~19-Sep)](https://amazonappdev2026.devpost.com/updates/46456-got-an-idea)
- The same update on Alexa+: "a single turn Q&A bot works, an agentic workflow that orchestrates across services or keeps context across sessions stands out more." — [Update 46456](https://amazonappdev2026.devpost.com/updates/46456-got-an-idea)
- **Bonus Points:** "During Stage 1 downselection, Amazon's internal review team assesses each submission's friction log entries (if provided) and passes a recommended bonus — up to 10% — to the Stage 2 judging panel along with the shortlisted projects. The Stage 2 panel applies this bonus to the submission's final spreadsheet score." — [Rules §6](https://amazonappdev2026.devpost.com/rules)
- Friction log format: "Optional – Friction Log Entries: specific task attempted, steps taken, expected vs. actual result, severity rating, workaround used, and actionable suggestion. Participants who submit friction logs score higher in judging (up to 10% bonus)." — [Rules §4](https://amazonappdev2026.devpost.com/rules)
- On how to submit it: "Link in description is fine. Saving the log in the same repo is certainly easier for judges though!" — [Forum 45430](https://amazonappdev2026.devpost.com/forum_topics/45430-inquiry-about-submission-mechanics)
- **Tie-break:** "the tied Submission with the highest score in the first applicable criterion listed above will be considered the higher scoring", which is Tech Implementation first. — [Rules §6](https://amazonappdev2026.devpost.com/rules)

**Judge guidance (Emerson Sklar)**
- "a strong fit would be something that you could really see people actually using on Alexa+, which brings new functionality to the platform or unlocks new experiences that are only possible in the current age of AI. Something that is a latent capability of modern LLMs or an existing feature of Alexa+ might score highly on Tech Implementation but would likely score poorly on Design and 'Quality of the Idea'."
- "Alexa+ is a generally a consumer-focused personal assistant".
- "Alexa is a voice-first platform, but not voice-only, and users expect a rich multimodal experience when using a device with a screen."
- Source: [Forum 45397](https://amazonappdev2026.devpost.com/forum_topics/45397-what-exactly-are-you-looking-for-in-the-alexa-track)

### Inferences
- "Penalized" is not the rules' word. The rules tell judges to "distinguish creative ideas from obvious ones" and list "basic MCP wrapper around an existing API" as obvious. In practice that scores lower on Quality of the Idea; it is not an automatic deduction.
- Tech Implementation decides ties, so engineering quality matters beyond its 25% weight.

### Gaps
- The Rules text itself has no 1–5 scale. It appears only in the update. How the friction-log bonus is computed exactly ("up to 10%" of what base) is not specified.

## Q4. Required deliverables: video, repo, licence, testing access, URL uptime, product feedback

### Takeaway
A submission needs:
- a text description;
- a GitHub repo (public with an open-source licence shown in the About box, OR private and shared with the listed reviewers);
- a public YouTube or Vimeo video under 3 minutes, in English;
- product feedback for every tool;
- the track and mini-challenge selections;
- the extra fields each mini challenge requires.

**Endpoint uptime conflict:** the FAQ says hosting is not required, but Emerson Sklar said twice in the forum that a hosted endpoint must stay live through judging.

### Cited Findings
**Repo**
- "Provide a URL to your code repository for judging and testing on GitHub. The repository must contain all necessary source code, assets, and instructions required for the project to be functional." — [Rules §4](https://amazonappdev2026.devpost.com/rules)
- "The repository must be either public and open source by including an open source license file OR private and shared with [testing@devpost.com] and the Amazon team". "For public repositories: this license should be detectable and visible at the top of the repository page (in the About section)." — [Rules §4](https://amazonappdev2026.devpost.com/rules)
- The Rules banner reads "September 16, 2026 UPDATE: Hackathon submission requirements: Code repository" (this is when private repos were allowed). — [Rules](https://amazonappdev2026.devpost.com/rules); [Update 46456](https://amazonappdev2026.devpost.com/updates/46456-got-an-idea)
- Private-repo collaborators: "chris-trag, knmeiss, giolaq, anishamalde, mosesroth, emersonsklar" plus testing@devpost.com. Invitations "expire after 7 days. Add the reviewers when you submit rather than weeks in advance". The FAQ list leaves out chris-trag, but the Rules and update include it. — [Rules](https://amazonappdev2026.devpost.com/rules); [FAQ](https://amazonappdev2026.devpost.com/details/faqs); [Forum 45264](https://amazonappdev2026.devpost.com/forum_topics/45264-private-repo-path-amazonappdev-is-an-organization-so-it-cannot-be-added-as-a-collaborator)

- Also required: identify the track(s) and mini challenge(s).
- AWS Builder: "Describe which AWS service(s) you used and how, in your Product Feedback answer."
- Open Source: "contribution URL, project repository URL, GitHub username, and a description of what you did, how it works, and why it matters."
